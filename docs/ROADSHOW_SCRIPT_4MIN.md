# 路演讲稿（4 分钟，无提问环节）

给站台讲解的队友。按页写，每页标时长；正文合计 3:50，留 10 秒余量。粗体是必须说出口的数字，其余可以换成自己的话。
原则：真机验证过的说"真机"，没上板的说"编译通过、待板"，不说加速比。

## 第 1 页 封面（0:15）

我们是你说的都队。题目是 Calculet NPU 的算子与模型移植。42 小时里我们做了两件事：补了官方算子库缺的双线性 Resize，
并把 Stable Diffusion 1.5 的 VAE 解码器搬上了 NPU 真机。

## 第 2 页 问题（0:25）

官方算子库 calBLAS 里只有最近邻放大，没有双线性插值。双线性插值是视觉预处理中的常见需求。我们的 VAE 移植则使用最近邻上采样，两条路线独立验收。
另外官方全部视觉算子都没进 calDNN 的图框架，赛题路线 A 明确要求"注册进引擎表、由图调用"。所以我们的目标是：
路线 A 把这个算子从零做到真机正确并接进图框架；路线 B 用一个真实子模型证明这条工具链能跑完整的网络。

## 第 3 页 算子（0:30）

Resize ×2，NHWC、bf16，PyTorch 的 align_corners=False 语义，边缘 clamp，中间用 f32 算、最后按 RNE 舍回 bf16。
普通版支持 C 到 128，通道分块版验证到 **C=256**。
工程上有两个点：docc 不接受 for 循环体里带结果的 if，所以我们把边界行三段展开，全程没有运行时条件分支；
横向加权用 0.25 和 0.75 两个常数在 cache 上做行偏移加法，不走 gather。

## 第 4 页 图接入（0:25）

calDNN 里新增 ResizeDesc、Op::Resize、Graph::resize，calBLAS 引擎表加 Resize 引擎，kernel 用 desc! 宏自注册。
主机侧从图到计划到地址绑定全链路通过，**5 项单元测试**。要说清楚的是：官方自己的图发射路径还没打通，我们做到的是规格与编排层的注册，上板走的是整程序路线。

## 第 5 页 验证方法（0:25）

我们不信单一参考。三路独立实现：复刻 kernel 运算次序的 CPU 版、按地址算式在一维内存里仿真的版本、还有一个独立坐标公式加自己写的 bf16 舍入。
**40 多项自动测试、13 种尺寸**，常量、脉冲、渐变、负值、边缘、通道分块边界，三路逐位一致。这份参考后来就是板上对比用的期望值。

## 第 6 页 VAE 移植（0:35）

SD1.5 的 VAE 解码器：latent 4×64×64 到 512×512 图，**35 个卷积、30 个 GroupNorm、1 个注意力、3 次上采样，100.7 MB 参数**。
我们写了三件工具：层表到 Rust 的代码生成器、fp32 权重到 bf16 参数块的打包器、按程序语义执行的 torch 仿真器。
程序切成 a、b1、b2a、b2b、c 五段，不是模型边界，是工具链约束：曾遇到常量循环展开导致单函数过大、超出链接器 21 位分支范围的问题。
GroupNorm 也因为这个限制自己写了两个 kernel。

## 第 7 页 审查抓到的 bug（0:30）

这是我们觉得最值得讲的一页。仿真器给了 52.8 dB，看起来一切正常，但代码审查发现两个错误。
一，按核分块的模板只由 0 号核调用，docc 把 num_cores 折成 2，每次只算一半数据，我们用探针程序在 docc 上证实了。
二，生成器查了一个不存在的算子名，NCHW 暂存区分成 0 字节，三段会越界写。
仿真器按张量名字执行，不建模地址和核分工，所以对这两个错误零检出。修复后重新编译，才拿去上板。

## 第 8 页 真机结果（0:35）

真机是 calculet-MS-A2，两芯粒，原始输出和对比文件都在仓库 evidence 目录里。
Resize：两个尺寸输出和 CPU 参考**逐位相同，1,114,112 个元素零差异**，三次重跑同哈希。
VAE：五段全部跑通，解出 512×512 的图，和 diffusers fp32 参考比 **PSNR 52.58 dB，最大误差 0.0536**，判据是 40 dB 和 0.08，通过。
整链 **34.6 秒**，其中 c 段 28.4 秒占 82%。这个时间包含部署开销，而且板端流带没开，所以只是现状记录，不是性能数据。
双核版 Resize 也上了板，输出和单核逐字节相同；墙钟只快一成，而且被固定开销稀释，我们不把它当性能结论。
